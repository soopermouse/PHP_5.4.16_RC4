## Known compatibility and security constraints

1. **Allocator failure (Patch200):** the process exits immediately rather than taking normal PHP fatal-error/user-handler/shutdown paths. The full external test suite found five patch-only `memory_limit` differences (including `ext/standard/tests/streams/bug61115-1.phpt`); the earlier selected subset found four. Suppressing this abort without a safe alternative would undo intended protection. Log/monitor worker restarts.
2. **Session upload progress (Patch200):** deliberately disabled in code even if `session.upload_progress.enabled=On`; eight upstream PHP tests fail. Do not rely on this feature. File uploads themselves are separate from upload-progress tracking.
3. **FTPS (Patch212):** servers that refuse TLS will now fail rather than receive cleartext credentials. Audit all `ftps://` use; prefer properly configured TLS endpoints, not `ftp://` fallback.
4. **SOAP (Patch210/211):** patched-only regression runs and source equivalence do not prove the vulnerable pre-patch failure mode, nor rule out memory-safety issues. Require independent review and controlled instrumentation where authorized.
5. **Session file writes (Patch206):** truncation-before-write avoids stale trailing bytes but can lose session contents if write fails. Verify filesystem full, permissions and partial-write handling on staging.
6. **FPM status path (Patch215):** it exposes operational metadata and must be disabled or restricted to a trusted administrative network/loopback. Output escaping does not make a public status endpoint safe.
7. **CVE-2026-129291 (PHP-FPM epoll):** PHP upstream dates the specific delayed-worker-cleanup path to 8.1.20/8.2.7, and this 5.4 tree does not contain that path. The same-named `fpm_child_close()` is not sufficient evidence of applicability. See `docs/CVE-2026-129291_PHP54_APPLICABILITY.md`; no speculative backport was added.
8. **EOL platform:** these patches cannot make PHP 5.4 or RHEL7 generally supported. Plan migration and retain a rollback VM.
